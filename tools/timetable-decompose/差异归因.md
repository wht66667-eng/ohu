# 为什么课表提取和 `campus-life-h5` 那套不一样

调查对象：现在仓库里**并存的三条课表抽取链路**，以及真机上唯一可用那份数据的样子。

结论全部基于实测，证据在 §6。**没有任何一处是读注释猜的。**

---

## 0. 一句话结论

**不是「同一份数据的两种解析」，而是「三条链路各读各的页面，而且真机上只有一种页面拿得到」。**

真机抓取留档（117 KB，5 个页面块）实测：

| 特征 | 出现次数 | 说明 |
| --- | ---: | --- |
| `table#Table6` + `span.time` / `span.kejie` / `span.didian` | **48** | 首页 `content_xs.aspx` 的周课表 —— **真机上真正能拿到的格式** |
| `table#Table1` + `周X第a,b节{...}` | **0** | 新版 Python 唯一认得的格式，**留档里从未出现** |
| 「教师」「老师」「teacher」 | **0** | 首页课表 HTML 里**根本没有教师字段** |

→ 所以「提取结果不一样」的第一原因不是解析 bug，是**两版看的是两个页面**，而其中一个页面的数据里压根没有教师。

---

## 1. 三条链路，三种页面

| # | 链路 | 入口 | 读的页面 | 抓取方式 | 教师 |
| --- | --- | --- | --- | --- | --- |
| 1 | **puppeteer 同步** `tools/timetable-sync/` | `海大课表一键同步.bat` | `content_xs.aspx` 首页 `table#Table6` | Playwright 登录 + 遍历 iframe，DOM 选择器 `span.time/kejie/didian` | **恒空** |
| 2 | **旧版云函数**（zip 里的 `getTimetable`） | HTTP `/query` | 登录落点页优先，失败才爬 `xskbcx.aspx` | 正则纯文本行 + 老式网格 | **恒空** |
| 3 | **新版 Flask**（当前页面在用） | HTTP `/api/timetable/*` | `xskbcx.aspx` 个人课表 `table#Table1` | BeautifulSoup 网格 | 有值 |

链路 3 才是 `xm-main` 现在真正跑的：`src/pages/schedule/ScheduleHome.tsx` → `src/lib/timetable.ts` → `VITE_TIMETABLE_API`（Flask）。
链路 2 在 `xm-main` 里**没有任何引用**（`src/` 与 `cloudfunctions/` 搜不到 `getTimetable`），目前只是历史实现。

---

## 2. 决定性根因：抓取落点不同

- **旧版**：`tryLoginZfnet` 拿到 POST 落点页正文 `navText`，`fetchZfnetSchedule` 先 `parseSchedule(login.navText)`；
  首页能解析成功就 `return`，**`xskbcx.aspx` 永远不会被请求**。
  解析优先级：JSON → `walkJouDayRowSchedule`（首页）→ `walkLegacyGrid` → `parseCourseListTable`。
- **新版**：`_resolve_menu_url` 解析「学生个人课表」菜单 → `fetch_schedule_html` 直接 GET `xskbcx.aspx?xh=...&gnmkdm=N121603`；
  **从不解析首页**。

两条路各自只认自己那一页，且都认不出对方那一页 —— 见 §6 的 2×2 实测。

---

## 3. 第二根因：旧版解析器会「误杀」个人课表

这条决定了**旧版没法简单改成读个人课表**：

`lib/parsers/grid.js` 的判空过滤器

```js
WEEKDAY_CELL_RE = /星期[一二三四五六日]|周[一二三四五六日]|(?:周|礼拜)[一二三四五六日]/
```

而个人课表每个格子都自带时间行 `周一第1,2节{第1-8周}` —— 含「周一」→ 命中 `WEEKDAY_CELL_RE` → `looksLikeCourse` 返回 `false` → **整格丢弃**。

实测：

| 格子文本 | `looksLikeCourse` | 结果 |
| --- | --- | --- |
| `海洋生态学\n周一第1,2节{第1-8周}\n李老师\nC文思302` | `false` | 丢 |
| `海洋生态学\n李老师\nC文思302`（去掉时间行） | `true` | 保留 |

→ 所以 `walkLegacyGrid` 跑个人课表页返回 `array len=0`（骨架找到了、格子全被判成表头），`parseSchedule` 最终 `null`。

**顺带**：`import`（Cookie 导入）通道的 seeds 是 `[xskbcx, kbcx, xs_main]`，同样会被这个过滤器拦掉，一路爬到首页，最终落到首页格式（教师空）。
**所以旧版无论走 zfnet 还是 import，输出都是首页那一份。**

---

## 4. 第三根因：字段与输出模型不同

### 4.1 教师

三条链路里两条 `teacher` 恒为空，看起来像偷懒，其实是**如实反映数据源**：

- `lib/parsers/jou-dayrow.js`：`teacher: ''`
- `tools/timetable-sync/scripts/parse-jou-html.mjs`：`teacher: ''`
- `public/last-snapshot.json`（真机同步产物）：13 门课 `teacher` **取值集合 = `['']`**

首页课表 HTML 里只有 `span.time` / `span.kejie` / `span.didian` 三个 span，**没有教师 span**（留档里 "教师/老师/teacher" 出现 0 次）。
只有 `xskbcx` 个人课表页才带教师 —— 而新版是唯一读那一页的。

### 4.2 教室

首页格式的教室来源不同，质量也不同：

- puppeteer 走 DOM：`span.didian` → `C文通325`（干净）
- 旧版云函数走正则猜：`楼|馆|室|文思|文通|苍梧` 或 `字母+2~4位数字` → 可能只拿到 `文思楼`

### 4.3 输出结构

| | puppeteer 链路 | 两个 HTTP 接口 |
| --- | --- | --- |
| 模型 | 「压缩课」`courses[]` + `parity` + `weeks` 字符串 + `startSection/endSection` | 「按周扁平行」`{week, day, sections[], name, teacher, room}` |
| 产物 | `public/last-snapshot.json`、`海大课表-WakeUp-最新.csv` | 接口响应 |
| 消费者 |（当前页面已不引用，属遗留） | `ScheduleHome.tsx` |

真机产物：**13 门课 / 405 行**。新版 mock 里的 7 门是手写子集，不是真数据。

## 5. 周次解析的真实差异（实测，最容易让人以为「课少了」）

### 5.1 离散周次：新版会丢周

真机数据里有离散周次课程（`形势与政策` → 周 `8、10、12`）。

| 输入 | 旧版 `parseZcd` | 新版 `expand_weeks` |
| --- | --- | --- |
| `1-10周` | 1…10 ✅ | 1…10 ✅ |
| `8-12\|双周`（**真机实际格式**） | 8,10,12 ✅ | 8,10,12 ✅ |
| `8-12周\|双周` | 8…12 ❌ 单双周丢失 | 8,10,12 ✅ |
| `8、10、12周`（顿号离散） | **8,10,12 ✅** | **只剩 12 ❌ 丢了 8 和 10** |
| `8周,10周,12周` | 8,10,12 ✅ | 8,10,12 ✅ |

新版丢周的原因：`_TIME_LINE_RE` 的周次字符类是 `[0-9\-]+`，**不含顿号 `、`** → 匹配不上 → 落到老式回退分支 → `_WEEKS_ONLY_RE` 把整行当成周次文本 → `expand_weeks` 的 `(\d+)周` 只捞到紧贴「周」的那个数字。

整格实测（不丢课，但周次错）：

```
输入: "形势与政策\n周三第7节{第8、10、12周}"
输出: {"name":"形势与政策","weeks":[12],"sec":[7,7],"teacher":"","room":""}
```

→ 用户看到的是「形势与政策只在第 12 周有课」，且教师/教室空。**这是相对旧版的回归。**

### 5.2 旧版的单双周顺序陷阱（潜伏，真机未触发）

`(8-12|双周)` 正确，但把「周」写在 `|` 前（`8-12周|双周`）就不再识别单双周。真机留档实测格式是前者，所以**当前不触发**，但值得留一条防御。

## 6. 实验证据

### 6.1 2×2 对照（同一份 HTML 分别喂两个解析器）

夹具：A = 首页 `Table6` 风格；B = 个人课表 `周X第a,b节{}` 风格。

| 输入 | 旧版（zip） | 新版（Python） |
| --- | --- | --- |
| **A 首页格式** | ✅ 26 rows，教师取值集合 `[""]` | ❌ `1007 parse-failed` |
| **B 个人课表格式** | ❌ `null` | ✅ 20 rows，教师 `["李老师","王老师"]` |
| **真机留档** | ✅ 420 rows，教师 `[""]`，**name/room 错位污染** | ❌ `1007 课表表头未识别` |

完美对角线 + 真机终审：**两版各只能解析对方解析不了的那种格式。**

逐解析器定位（旧版跑夹具 B）：

```
jou-dayrow(walkJouDayRowSchedule) -> null
grid(walkLegacyGrid)              -> array len=0     ← 骨架找到，格子全被丢
course-list                       -> null
```

留档来自 `桌面/海大课表-抓取调试.html`（`tools/timetable-sync` 的调试产物，2026-09-12）。

## 7. 前端会进一步放大差异

`src/pages/schedule/ScheduleHome.tsx`：

1. **默认周**：`guessCurrentWeek()` 按 `2026-08-31` 起算 → 打开时可能落在无课周，看起来「课表是空的」。
2. **节次上限**：`NS = 11` 且 `clamp(..., 1, 11)` → 第 12 节被压到第 11 节。真机 `maxWeek=20` 说明节次/周次的空间比前端假设的宽。
3. **合并分组键**：`${day}|${name}|${room}|${teacher}` —— `teacher` 恒空时，**同一天同一门课的不同记录会被合进同一格**；换了有教师的通道后，同一门课会拆成两格。这条会让「同一份 rows」也显示得不一样。

---

## 8. 建议怎么对齐

按性价比排序：

1. **把「首页 `Table6`」定为唯一数据源**。真机上只有它拿得到；`walkTable6` 的 DOM 选择器（`span.time` / `span.kejie` / `span.didian`）是已经被 13 门课验证过的可靠锚点。新版 Python 若要继续用，应把 `parser.py` 增加 Table6 分支，而不是只认 `Table1`。
2. **修 `expand_weeks` 的顿号离散周次**（`8、10、12周` 现在只剩 12）。改动很小、影响直接可见：把周次字符类补上 `、`，或先做顿号归一化。这是相对旧版的真实回归。
3. **教师一栏改成「数据源不提供」的显式语义**，而不是留空白 —— 否则用户会以为是解析失败。若要真教师，必须新增抓 `xskbcx` 的通道。
4. **若真要走 `xskbcx` 通道，先修旧版的 `WEEKDAY_CELL_RE` 误杀**（§3），否则旧版读那一页恒为空。
5. **给 `parseZcd` / `expand_weeks` 补一条 `(N-M周|单双周)` 的防御**（潜伏问题，真机暂未触发）。
6. **不要喂多页拼接**。实测把 5 个页面块拼在一起喂旧版解析器，`name`/`room` 会出现错位污染（如 `name="…概论 C文通325"`、`room="5-6节 (1-8周)海洋生态学基础 C文思302"`）。真实链路只应喂单页。

- `public/last-snapshot.json` 与 `tools/timetable-sync`、`tools/timetable-extension` 目前**没有代码引用**，属于遗留链路；要么接回去，要么归档，避免下次又出现「三份实现互不认识」。
