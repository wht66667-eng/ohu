# 云端推送提醒：选型方案（2026-10-14）

> 结论先行：**能不能做，先看主体资质，不看技术。** 没有企业主体时，真实可用的厂商通道只有
> **华为**（+魅族）；小米 / OPPO / vivo / 荣耀 全部要求**企业开发者账号**（小米还额外要求已上架）。
>
> 而现有「本机闹钟」已经能在**杀掉 App 之后准时响**（见 `android-reminder-guide.md`）。所以本次
> 建议是：**暂不把上课提醒迁到推送**，只把推送当作「服务端主动下发新内容」的补充通道，
> 且第一期**只接华为通道**。

---

## 1. 现状：提醒为什么已经够用

| 项 | 事实 |
| --- | --- |
| 通知依赖 | 只有 `@capacitor/local-notifications@^7.0.7`，**无任何推送 SDK**（无 FCM / 个推 / 极光 / TPNS） |
| 调度方式 | `AlarmManager` 精确闹钟，到点由 Manifest 里的 `TimedNotificationPublisher` 广播弹通知，**与 App 进程无关** |
| 后台自续期 | 原生 `ReminderPlanStore` 保存**未来 210 天**课表提醒快照，每天 **01:05** 静默补排未来 7 天 |
| 开机恢复 | `BOOT_COMPLETED` / `MY_PACKAGE_REPLACED` → `resume()` → `replenish()`；插件侧 `LocalNotificationRestoreReceiver` 另有一层（本项目已打补丁：只恢复 owner 自己的、过期提醒直接删掉不复活） |
| 会失效的情况 | ① 系统「强行停止」过 App（Android 会清掉全部闹钟且不再收 BOOT_COMPLETED）② 电池优化冻结 ③ 精确闹钟未授权 ④ 用户关掉「开机恢复」 |

**所以推送的增量价值只有一条**：用户没打开 App 时，服务端能主动下发新内容（公告、临时调课、老师通知）。
课表/待办/考试这类**本来就由本机闹钟覆盖**的提醒，迁到推送反而是降级（推送依赖网络 + 厂商配额 + 离线有效期）。

## 2. 决定性约束：厂商通道申请门槛

来源：EngageLab《厂商通道参数申请指南》（各家官方流程的整理）。

| 厂商通道 | 是否需要上架 | 账号要求 | 个人开发者可用 |
| --- | --- | --- | --- |
| 华为 | 否 | 个人开发者即可 | ✅ |
| 魅族 | 否 | 个人开发者即可 | ✅ |
| FCM | 否 | 个人即可 | ❌ 国内网络不可用 |
| 小米 | **是** | **企业开发者** | ❌ 个人账号登录会提示「当前没有推送/审核权限」 |
| OPPO | **是** | **企业开发者** | ❌ |
| vivo | **是** | **企业开发者** | ❌ |
| 荣耀 | 否 | **企业开发者** | ❌ |

补充：五大商店（华为 / 小米 / OPPO / vivo / 应用宝）上架还要求 **软件著作权证书 + ICP 备案 +
工信部 APP 备案 + 可公开访问的隐私政策外链 + 加固**，社交类应用另有安全评估报告。
个人主体一般只能上架非经营性工具类。

**推论**：在没有企业主体、且 App 主要靠直链/桌面 APK 分发的前提下，
做「全机型推送」这件事**卡在资质而不是代码**。

## 3. 成本参考（2026-10-14 查证，以官网为准）

| 服务 | 免费额度 | 超出后 | 厂商通道覆盖 | 离线有效期 |
| --- | --- | --- | --- | --- |
| 腾讯云 TPNS | 按量计费**当日 DAU ≤1000 不产生费用**；慈善类 App 永久免费 | 广州/上海 **0.0032 元/DAU/天**；包年包月 **800 元/万 DAU 月峰值/月**（最小 1 万起） | 小米、华为、荣耀、鸿蒙、魅族、vivo、OPPO、APNs、FCM + 自建通道 | 默认 24h，最长 72h |
| 个推 | **推送条数无限制** | VIP / SVIP 才有智能配额、余量监控等 | 华为、荣耀、小米、OPPO、VIVO、魅族 + 自建通道 | 最高 3 天 |
| 极光 JPush | 基础版免费 | 企业版按年计费 | 主流厂商通道 | — |

个推免费版的接口限额值得注意：**全量推送 20 次/天**、单推 250 万次/天、列表推 200 万次/天。
对本项目（按账号单推、量级很小）完全够用。
TPNS 的注意点：基础推送 API **200 次/小时**。

## 4. 接入工作量（本仓库视角）

> ⚠️ 全部**必须重打 APK**，热更（Capgo OTA）带不动原生 SDK。

1. **原生**
   - 接 SDK（TPNS 或个推），`AndroidManifest` 补权限 / receiver / service
   - 逐个厂商上传**包名 + 签名指纹**取得通道参数（第一期只有华为）
2. **前端**
   - deviceToken 上报（含首次注册与刷新）
   - 账号绑定 / 解绑：**登出必须解绑**，否则会串号推给别人
   - 通知点击路由到对应页面（公告 / 课表 / 待办）
   - 通知总开关、免打扰时段，与现有 `ReminderBootStore` 的 owner 隔离模型对齐
3. **后端**
   - CloudBase 新集合（token + ownerUid + 平台 + 厂商），配 RLS
   - 云函数 `pushSend` 调推送 REST API
   - 如需「定时群推」再加定时触发器（个推免费版全量仅 20 次/天，要留意）
4. **合规**
   - 隐私政策补**第三方 SDK 清单**与所收集信息
   - 首次启动弹窗（已有 `FirstRunHost`）明示推送目的 + **一键关闭**，不得默认勾选
   - 最小必要：只取 OAID，**不要取 IMEI**
   - 区分**服务类推送**（订单/课务，无需单独同意）与**营销类推送**（必须明确授权 + 便捷退订）
   - 推送 SDK 常带「自启动 / 关联启动」与 `QUERY_ALL_PACKAGES`，是工信部通报高发点，需评估

## 5. 建议路线

**第一期（可落地）**
1. 维持上课提醒走本机闹钟**不动**（更可靠）。
2. 接 **个推免费版**（或 TPNS），**只开华为通道**，用来推「公告 / 临时调课」这类服务端主动内容。
3. 先把「App 内通知中心 + 打开即拉取」这条链路补齐（成本最低，覆盖大部分场景）。

**第二期（拿到企业主体、上架五大商店之后）**
4. 补齐小米 / OPPO / vivo / 荣耀通道，把到达率做上去。
5. 再评估是否把部分提醒迁到推送（例如需要服务端撤销/改期的通知）。

**不建议做的事**
- ❌ 把上课提醒改成推送：本机闹钟已能在杀后台后准时响，推送只会引入网络与配额的不确定性。
- ❌ 用「服务端定时触发 + App 长连接」当推送：App 被杀即断，等于没有。
- ❌ 在没有企业主体的前提下先写推送代码：通道参数申请不到，写完也上不了线。

---

## 6. 待你确认

- 是否有**企业主体**（营业执照 / 软著 / ICP 备案）？有 → 走第二期设计；没有 → 只做第一期。
- 第一期是否就按「个推免费版 + 仅华为通道」推进？（如需换 TPNS，接口封装层可做成可替换）
- 「公告 / 临时调课」这类内容，是否接受**只做 App 内通知中心**（不做系统推送）？若能接受，
  这一期可以零 SDK、零资质、零成本先上线。
