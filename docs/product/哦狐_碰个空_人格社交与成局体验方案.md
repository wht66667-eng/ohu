# 哦狐「碰个空」人格社交与成局体验方案

版本：1.0  
整理日期：2026-10-30  
依据：用户提供的《OHU_碰个空_人格社交与成局体验升级方案_v2.0》，按哦狐当前页面、API 与本地 SQL 收敛。  
状态：实施方案；不代表功能已实现、数据库已执行或服务已部署。

## 1. 产品定位

「碰个空」继续作为哦狐里的校园活动组队功能，帮助同学从“想做什么、什么时候有空”走到“活动真的成行”。兴趣和社交风格用于降低组队摩擦；人格玩法是可选的趣味资料，不做交友门槛，也不替用户决定谁适合谁。

**产品表达：找到有空的人，也找到合拍的搭子。**

不另建账号、聊天或好友关系系统。优先复用哦狐账号、课表、活动邀请、二维码、提醒、举报和聊天能力。

## 2. 现有能力基线

以下依据当前工作区源码，不等于生产数据库或线上服务已核验。

| 能力 | 当前实现 |
|---|---|
| 活动项目 | 自习、台球、麻将、羽毛球、吃饭、其他；代码和本地 SQL 都限制活动值 |
| 时间与人数 | 未来日期范围、30/60/90/120 分钟、2–20 人；参与者选择半小时空档 |
| 课表参考 | 登录用户可把已同步课表中的空档作为草稿带入，仍需手动确认 |
| E/I | 发起人和参与者可选 E、I 或不限；发现时也可选偏好 |
| 16 型狐格 | 本地源码已加入 16 款阿狐头像、12 道原创校园情境题、结果确认和手动选型；个人类型和期望类型可选，测评答案不保存 |
| 邀请和公开发现 | 同校公开活动或私密邀请；支持链接/二维码；公开发现当前依赖手填学校名称 |
| 推荐与确认 | 按学校、活动、时间可用性筛选；E/I 偏好用于排序。发起人选择所有已回复成员共同选择的连续时段 |
| 活动管理 | 我的活动、报名回复、发起人确认时间、成员退出、发起人结束活动 |
| 并发约束 | 本地 SQL 通过行锁和唯一约束处理重复报名、人数上限等；线上执行状态未核实 |

### 当前缺口和边界

- `campus` 是用户填写的文本，不是标准学校 ID，也不能证明已核验同校。
- 当前没有独立的“确认成员”状态。参与者回复代表提交参加意向和空闲时段；全员时段重合后由发起人选定时间。
- 确认时间后，现有 SQL 禁止成员修改回复或退出；没有独立的改期、取消、地点确认和状态历史。
- 活动详情尚无结构化地点、活动提醒联动、聊天入口和反馈/再次约局闭环。
- 兴趣标签尚未实现。16 型狐格已在本地客户端实现，但服务端迁移未登记／部署，线上匹配排序不可确认。
- 本地 `meet-invitations.sql` 未登记在数据库部署清单中；生产结构和函数版本未知。不能直接执行或据此声称上线。
- 初始审计发现 `meet_discover` 复用详情 payload，会多返回参与者昵称、E/I 与个人半小时空闲汇总；本地 SQL 源码现已改为最小活动摘要且要求已登录账号，客户端发现结果也使用摘要类型。后续源码收敛将 `meet_get` 改成摘要，并新增 `meet_get_member`：发起人账号、参与者账号或匹配的访客参与令牌可读取成员和时段，其余访问者只拿到摘要；退出 RPC 对无效凭证和成功退出都只返回摘要。客户端用 `detailsVisible` 区分预览和成员详情。相关 SQL 尚未登记、执行或部署，生产 RPC/权限状态仍未核实。

## 3. 贴合现有碰个空的功能结构

### 3.1 快速找搭子

保留免人格流程：选活动、日期、时长和本人确认有空的时间。E/I 扩展为“我是”与“希望搭子”两个独立偏好：

- 我是：E 人、I 人、看场合、暂不填写。
- 希望搭子：E 人、I 人、都可以、随机认识。
- 活动兴趣：选择活动项目及少量可维护兴趣标签。

没有偏好时仍能看到其他符合时间和活动条件的组队。E/I 只作软排序，不硬性拒绝成员；结果展示真实理由，例如“时间段重合”“活动项目相同”“你选择了 I 人偏好”，不显示未经验证的匹配百分比。

### 3.2 活动项目与兴趣标签

先完善现有“其他活动”的输入体验，再评估扩展 SQL 活动枚举。候选项目：自习、吃饭、台球、麻将、羽毛球、跑步、散步、看电影、探店、桌游、校园探索、其他。自定义名称需服务端校验长度和内容；不能只加前端按钮而提交数据库不支持的值。

首版兴趣标签数量保持精简，服务于活动发现和自愿资料展示，不另造兴趣信息流。组队资格仍以活动开放状态、人数和用户确认的空闲时间为准。

### 3.3 可选狐格资料

当前客户端已提供 16 型狐格资料：16 款阿狐可在图鉴弹层中浏览并直接选型，也可完成 12 道原创校园情境题后确认结果；允许随时改选或暂不填写。阿狐形象以统一透明 sprite sheet 绘制，插画仅作趣味表达。个人类型和期望搭子类型分开设置；测评答案只存在当前测评会话，完成后仅保存用户确认的类型到本机账号分区资料。参与活动时可再次修改。服务端 SQL 草案仅在获授权的活动详情中向成员显示本人主动填写的类型；期望搭子类型不向成员公开。

人格仅作趣味标签，不表示能力、性格优劣、可信度或关系成功率。当前测评依据每维 3 道二选一情境题做简单计数；它不是 MBTI 官方工具、诊断或专业测量，不应宣传为科学测评。用户需在结果页主动确认，之后也可手动改型或清除；不做题、不填类型均不影响使用。客户端以类型作为查询条件请求服务端，只用于推荐顺序；发现卡片只接收汇总的偏好匹配标记，不读取或显示其他用户的人格。数据库 SQL 尚未登记／执行，因此线上同步和排序尚未生效或核验；本机资料不等同云端同步。

### 3.4 狐格实验室和关系内容

如果前述活动闭环稳定且确有使用需要，再增加 12 道情境题、四维偏好结果和静态关系内容。16×16 矩阵可先作为不使用个人资料的趣味内容。双人或群体分析只使用双方明确同意公开的信息；不生成“最佳朋友”或“98% 匹配”等确定性标签。

### 3.5 活动成局中心

继续以现有“我的活动”为统一入口，逐步按状态展示：开放报名、待定时间/地点、已成局、进行中、已结束、已取消。详情后续补充：

- 参与者与发起人权限、报名和变动记录。
- 地点提案/确认、改期、取消和成员退出。
- 自愿参与、可跳过的破冰卡片。
- 活动结束反馈、再次约局和基于真实记录的非竞争徽章。
- 复用哦狐聊天；不默认建群。
- 用户确认后添加待办/日程提醒；改期更新、取消撤销。

## 4. 推荐规则

1. 活动开放、未满员，学校筛选条件符合。
2. 用户主动确认的空闲时间满足活动时长，所有必要时段连续重合。
3. 活动项目或兴趣标签相符。
4. 用户选择的 E/I 和社交节奏偏好相符。
5. 课表只表示“可能没课”，不推断用户必然有空；用户确认的个人空闲优先。

人格、兴趣和社交节奏只影响软排序，不成为隐形过滤。随机破圈表示关闭这些软偏好，不绕过学校、活动状态、时间和权限条件。缺少标准学校目录与授权验证时，界面继续说明“按填写的学校名称筛选”，不显示“已认证同校”。

## 5. 成局状态与服务端约束

目标状态流：

```text
开放报名 → 达到目标人数 → 确认时间 → 确认地点 → 已成局
    → 进行中 → 已结束
       ↘ 改期协商 / 取消 / 成员退出
```

这只是目标状态，不代表当前 SQL 已实现。先核实生产数据库和函数，再通过向后兼容迁移增加所需字段、状态记录和 RPC。

服务端事务应保证：

- 不超员、不重复报名；成员退出与发起人确认并发时状态一致。
- 只有有权成员可以提议改期/地点或取消；活动关闭后不能加入。
- 改期经相关成员确认后更新活动时间和提醒；取消后撤销提醒。
- 已结束活动不能被普通客户端恢复为开放状态。
- 状态变更可审计且请求幂等，网络重试不重复操作。

## 6. 隐私、安全与治理

- 不公开完整课表、个人精确空闲计划、宿舍或私人住址；公开发现只返回活动摘要。
- 邀请预览与报名后详情分开；本地源码已区分摘要 RPC 与成员详情授权，但待生产迁移登记、基线核验和验证，不能把源码修改视为线上已修复。
- 人格默认私有；匹配使用和对外展示分别授权。
- 自选学校与已核验学校分开。没有学校验证能力时不显示核验徽标。
- 举报/屏蔽复用现有管理后台，明确对象、处理状态和申诉；屏蔽后从公开推荐排除。
- 破冰题可跳过，不要求用户披露私人信息。
- 不新增账号、聊天、学校认证或第二套活动系统。

## 7. 分阶段实施

### 阶段 0：权限与数据基线

- 本地发现及邀请预览/详情源码已收敛；仍需核实生产 SQL/RPC、匿名与认证权限、公开响应字段和迁移登记缺口。
- 需验证邀请预览、加入后详情、发起人和成员的可见范围；不得把本地 SQL 变更当成线上权限已生效。
- 核对发现排序与 E/I 语义，不把筛选推荐描述成自动配对。

### 阶段 1：成局闭环

- 地点提案/确认、改期、取消、成员退出和状态历史。
- “我的活动”按状态组织；联动提醒与现有聊天。
- 活动项目服务端契约及举报/屏蔽权限一致。

### 阶段 2：兴趣社交

- 兴趣标签、社交节奏和 E/I/看场合偏好，均可跳过。
- 发现软排序和可解释推荐理由；用户可关闭人格/兴趣影响。
- 可选破冰题和活动主题。

### 阶段 3：狐格卡和趣味人格

- **本地客户端已实现**：16 款阿狐人格插画、手动选型、12 道原创情境题、结果确认、可选本人类型／期望搭子类型和本机保存。
- **本地接口与 SQL 草案已改**：活动创建／回复带入两类类型；发现接口计算双向偏好汇总标记并只用于软排序，不过滤活动；公开卡片不暴露成员人格。
- **线上仍待完成**：先核对生产 schema、RPC、权限和数据库迁移记录，再制定向后兼容迁移并通过隔离环境验证；当前 SQL 源未登记、未执行，不能声称线上已经生效。
- 测评结果可改、可清除，不影响使用资格；答案只在测评会话中处理，确认的类型本机保存。
- 静态关系矩阵优先于使用个人资料的双人/群体分析。

### 阶段 4：长期搭子

- 双方同意后标记“一起活动过/愿意再次组队”。
- “再次约局”复用活动流程；徽章只依据真实完成记录。
- 不做人格等级、好友排行榜或虚构活跃指标。

## 8. 首批代码工作与验收

按依赖自动连续推进，每个功能完成后更新项目台账并继续下一项，不等待人工逐项确认：

1. **隐私审计**：本地源码已为 `meet_discover` 拆分公开摘要并要求登录，也已将邀请预览与成员详情分离；生产服务仍需只读核对 `meet_get`、`meet_get_member`、`meet_discover`、`meet_payload` 的权限和字段。
2. **成局状态闭环**：地点、改期、取消、退出、状态记录；先完成生产数据库基线和兼容迁移设计。
3. **提醒与聊天衔接**：复用现有模块，明确授权、更新与撤销。
4. **兴趣和社交偏好**：软排序、透明理由、跳过和退出选项。
5. **狐格资料与测评**：客户端与本地 SQL 草案已实现；待生产数据库基线确认后做兼容迁移和隔离环境验证。

验收包括：不填写人格也可完成组队；偏好只软排序且理由真实；课表空档不等于个人有空；全员时段满足时长才可确认；并发满员/重复报名/退出/确认/改期/取消不破坏状态；未加入用户看不到非公开成员资料和精确空闲；提醒随改期/取消更新；不显示虚构匹配率、活动人数或徽章。

## 9. 暂不纳入

- 自动建立长期好友关系，或未经双方同意推荐“最佳朋友”。
- 把人格当作科学兼容度、可信度、能力或交友资格。
- 公开个人日程、详细课表、宿舍或私人联系方式。
- 没有数据库基线和审核能力时扩展公开匹配 SQL。
